# 모임 이벤트 관리 웹 MVP 기획서

## Context

수영, 헬스, 친구 모임 등을 진행할 때 주최자는 공지, 참여자관리, 카풀, 정산을 카카오톡·엑셀·계좌이체 화면 등 서로 다른 채널로 흩어서 관리하고 있어 번거롭고 누락이 잦다. 이 기획은 위 4가지 업무를 한 곳에서 처리할 수 있는 웹 MVP를 설계해, 실제 사용 반응을 빠르게 검증하는 것을 목표로 한다.

사용자 확인 사항:

- MVP 범위: 공지·참여자관리·카풀·정산 4개 기능 모두 **얕게** 포함
- 정산: 실제 송금/결제 연동 없이 **계산·기록만**
- 카풀: 경로 매칭 없이 **좌석 등록/신청만**
- 이번 산출물은 **기획 문서만** (코드 구현은 별도 진행)

이 저장소(nextjs-supabase-app)는 현재 `profiles`, `instruments` 테이블만 있는 초기 Next.js + Supabase 스타터 상태이며, 실제 구현 시 이를 기반으로 확장하는 것을 전제로 데이터 모델·화면 구조를 그렸다.

---

## 1. 타겟 사용자 & 페르소나

- **Primary — 모임 주최자**: 수영/헬스/친구모임 등 정기·비정기 소규모 모임을 직접 운영하며 공지·인원파악·카풀·정산을 모두 떠맡는 사람
- **Secondary — 모임 참여자**: 공지 확인, 참여 신청, 카풀 좌석 신청, 본인 정산 금액 확인이 필요한 사람

## 2. 핵심 문제

주최자 업무(공지/참여자관리/카풀/정산)가 여러 툴에 흩어져 있어 관리 비용이 크고 누락이 발생한다. 참여자 입장에서도 정보가 흩어져 있어 확인이 번거롭다.

## 3. MVP 핵심 기능 (4개, 각각 얕게)

### 3.1 모임(이벤트) 관리 — 골격 기능

- 모임 생성: 제목, 설명, 카테고리(수영/헬스/친구모임/기타), 일시, 장소, 정원
- 모임 목록/상세 조회, 수정/취소

### 3.2 공지

- 모임별 공지 텍스트 작성 및 목록 노출 (첨부파일·푸시알림 없음, 웹 접속 시 확인하는 방식)
- 작성 권한은 항상 해당 모임의 주최자 1인 (공동 주최자는 범위 밖)

### 3.3 참여자 관리

- 로그인 사용자가 모임에 참여 신청 (동일 모임에 중복 신청 불가)
- 주최자가 신청을 승인/거절 (**수동 승인만 지원 — 정원 내 선착순 자동 확정 옵션은 두지 않음**, 결정사항 참고)
- 주최자용 참여자 목록, 참여자용 "내 참여 모임" 목록
- 참여 취소

### 3.4 카풀 (좌석 등록/신청만)

- 운전자가 출발지(텍스트)·출발시간·좌석수로 카풀 등록
- 참여자가 좌석 신청 → 운전자가 확정 (신청 1건 = 좌석 1석. 여러 좌석이 필요하면 여러 번 신청)
- **좌석수(seat_count)를 초과해 확정하려는 시도는 시스템이 확정 자체를 막는다** (경고만 하고 허용하지 않음, 결정사항 참고)
- 지도 연동, 경로 자동 매칭은 범위 밖

### 3.5 정산 (계산·기록만)

- 비용 항목 등록: 항목명, 금액, 결제자
- **한 비용 항목에 결제자가 여러 명일 경우, 해당 항목 금액을 결제자 수 기준 1/N으로 나눠 각자 결제한 것으로 기록한다** (결정사항 참고)
- 참여자 수 기준 1/N 자동 계산 (커스텀 비율은 범위 밖)
- 참여자별 정산 금액은 비용 항목이 바뀔 때마다 다시 계산되는 스냅샷이며, "정산 완료" 체크만 사용자가 직접 보존
- 실제 송금/PG 연동 없음

## 4. 명시적 제외 범위 (Out of Scope)

- 실시간 채팅, 푸시/카톡 알림 연동
- 결제·PG 연동
- 지도 기반 카풀 경로 매칭
- 커스텀 비율 정산, 다중 통화
- 네이티브 모바일 앱
- 리뷰/평점, 소셜 기능(팔로우 등)
- 모임 공개/비공개(초대 링크 기반 비공개 모임) — 모든 모임은 공개 (결정사항 참고)

## 5. 핵심 사용자 플로우

1. 주최자가 모임 생성 → 공지 작성
2. 참여자가 모임을 조회 → 참여 신청
3. 주최자가 신청 승인
4. (선택) 운전자가 카풀 등록 → 참여자가 좌석 신청 → 운전자 확정
5. 모임 종료 후 주최자가 비용 항목 입력 → 시스템이 1/N 계산 → 참여자별 정산 금액 확인 및 완료 체크

## 6. 재사용 가능한 기존 자산

구현 착수 시 아래 자산은 그대로 재사용하고 새로 만들지 않는다.

- **`profiles` 테이블**: `full_name`, `avatar_url`, `username` 등 이미 보유 → 참여자/운전자 표시에 추가 컬럼 불필요.
- **`app/instruments/page.tsx` 패턴**: Server Component + `Suspense` + `supabase.from(...).select()` 직접 호출. `/events`, `/events/[id]` 등 신규 페이지의 기준 패턴으로 사용.
- **`proxy.ts` 인증 게이팅**: `lib/supabase/proxy.ts#updateSession`이 `/`, `/login*`, `/auth*`를 제외한 모든 경로를 이미 인증 필수로 리다이렉트 처리하므로, `/events`·`/my` 등을 `/protected` 하위에 중첩할 필요 없음 (`/instruments`와 동일하게 최상위에 배치).

## 7. 데이터 모델 초안

기존 `profiles` 테이블(Supabase Auth 연동 사용자)을 그대로 재사용하고, 아래 테이블을 신규로 추가하는 것을 제안한다.

| 테이블               | 주요 컬럼                                                                                                                                         | 비고                                                                                                                                      |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `events`             | id, host_id(FK→profiles), title, description, category, location, event_datetime, capacity, status(open/closed/cancelled), created_at, updated_at | 모임                                                                                                                                      |
| `event_participants` | id, event_id(FK), user_id(FK), status(pending/approved/rejected/cancelled), applied_at                                                            | 참여 신청. UNIQUE(event_id, user_id)                                                                                                      |
| `announcements`      | id, event_id(FK), content, created_at                                                                                                             | 공지. 작성자는 항상 해당 event의 host_id이므로 별도 author_id 없음                                                                        |
| `carpools`           | id, event_id(FK), driver_id(FK), departure_point, departure_time, seat_count, created_at, updated_at                                              | 카풀 등록                                                                                                                                 |
| `carpool_requests`   | id, carpool_id(FK), passenger_id(FK), status(pending/confirmed/rejected), created_at, updated_at                                                  | 좌석 신청 (1건 = 좌석 1석). confirmed 건수가 carpools.seat_count를 초과하면 확정 불가                                                     |
| `settlements`        | id, event_id(FK), payer_id(FK), item_name, amount, created_at                                                                                     | 비용 항목. 결제자가 여러 명이면 항목을 결제자 수만큼 분할해 각각 1행으로 등록(각 행 amount = 원금액/결제자 수)                            |
| `settlement_shares`  | id, event_id(FK), user_id(FK), amount_owed, is_paid(bool)                                                                                         | 참여자별 분담액. UNIQUE(event_id, user_id). settlements 변경 시마다 amount_owed를 재계산하는 파생 스냅샷 — is_paid만 사용자 입력으로 보존 |

RLS 방향:

- 쓰기(생성/수정/삭제)는 `auth.uid() = host_id`(events/announcements/carpools 등 주최자 소유 리소스) 또는 `auth.uid() = driver_id`/`payer_id` 등 소유자 기준으로 제한.
- 조회는 해당 이벤트의 승인된 참여자만: `EXISTS (SELECT 1 FROM event_participants WHERE event_id = ... AND user_id = auth.uid() AND status = 'approved')` 패턴을 공지/카풀/정산 조회 정책에 공통 적용.
- 세부 정책 SQL은 구현 단계에서 작성.

## 8. 화면 구조 (Structure-First)

- `/events` — 모임 목록
- `/events/[id]` — 모임 상세 (공지 / 참여자 / 카풀 / 정산 탭)
- `/events/new`, `/events/[id]/edit` — 모임 생성/수정
- `/my` — 내가 주최한 모임 / 참여한 모임
- 위 경로들은 `/protected` 하위가 아닌 최상위 라우트로 배치 (`/instruments`와 동일한 위치 규칙). `proxy.ts`가 `/`, `/login*`, `/auth*`를 제외한 모든 경로를 이미 인증 필수로 처리하므로 별도 게이팅 설정 불필요.
- 기존 `/auth/*` 로그인 플로우 재사용 (신규 auth 구현 불필요)
- (후속) 홈 `/`의 CTA를 `/events`로 연결하는 작업은 구현 단계 후속 작업으로 남겨둠

## 9. 로드맵 (얕게 4개 모두 → 반응 보고 확장)

- Phase 0: 모임 CRUD + 참여자 신청/승인 (골격)
- Phase 1: 공지
- Phase 2: 카풀 좌석 등록/신청
- Phase 3: 정산 계산/기록
- Phase 4 (MVP 이후, 사용자 반응 확인 후): 알림, 결제 연동, 지도 기반 카풀 매칭 등 확장 검토

## 10. 성공 지표 (제안)

- 모임 생성 수, 모임당 평균 참여 신청 수
- 카풀/정산 기능 실사용률 (등록만 하고 안 쓰는지 확인)
- 주최자 재방문율 (다음 모임도 이 도구로 만드는지)

## 11. 결정 사항 (열린 질문 답변 완료)

| 질문                                                                 | 결정                                             |
| -------------------------------------------------------------------- | ------------------------------------------------ |
| 참여 승인을 항상 수동으로 할지, 정원 내 선착순 자동 확정 옵션도 둘지 | **수동 승인만 지원**                             |
| 비용 항목별 결제자가 여러 명일 때 처리 방식                          | **1/N** — 항목 금액을 결제자 수만큼 균등 분할    |
| 모임 공개/비공개(초대 링크 기반 비공개 모임) 지원 필요 여부          | **지원하지 않음** — 모든 모임은 공개             |
| 카풀 좌석이 실제 seat_count를 초과해 확정되려 할 때 UX               | **확정 자체를 막음** (경고만 하고 허용하지 않음) |

---

이 문서는 기획서이며 코드 구현은 포함하지 않는다. 구현 착수 시 위 데이터 모델을 기준으로 마이그레이션(`supabase/migrations` 디렉터리 신설 권장)·RLS 정책·페이지 스캐폴딩을 이어서 진행한다.
